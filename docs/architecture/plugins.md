# 07. Plugins

Rafael's requirement R3: *the language can be extended with plugins*. This
document answers what a plugin is, what it may do, and above all what it may
**not** do. Status: **agreed** (Michelangelo, Bob), owner: Michelangelo (surface rules and
wording). The sandbox mechanics (Wasm host, WIT interfaces) are in
[02](compiler-architecture.md) §2.9 (`verse-plugin`) and are summarised here
only where they change what a user sees.

## 7.1 The two rules

1. **A plugin never changes the language.** No new keyword, operator, literal,
   annotation, macro or grammar rule. A `.vs` file parses, type-checks and
   means exactly the same on every machine, whatever plugins are installed.
2. **A plugin never changes what a valid program means.** It may read the
   program, report on it, write new source files next to it. It may not rewrite the program behind the author's back.

Why: spec §1.4 promises one spelling per meaning, and a reader must be able to
understand a file by reading that file. A syntax plugin would turn "what does
this line mean?" into "which plugins does this project use?". Flexibility
comes from packages, traits and generated code, all of which are visible
Verse.

*Script and compile modes.* Plugins run at `check` and `build` time, never
inside the program. So a plugin cannot make `verse run` and `verse build`
differ. The only plugin output that reaches the running program is ordinary
Verse source (7.3), and it is present in every tier. Packages written as Wasm
components (7.4) are dependencies, not plugins, and run the same way in every tier.

## 7.2 What a plugin can be

Four kinds, and no others in 0.1. A plugin declares exactly one kind in its
manifest.

| Kind | What it does | Reads | Writes | Example |
|------|--------------|-------|--------|---------|
| `lint` | Reports warnings and suggested edits | typed program (read only) | diagnostics | "this loop can be `.map(…)`" |
| `generator` | Produces Verse source files from a description | its declared inputs | files in `generated/` | records from a JSON schema |
| `bindgen` | A generator for foreign libraries | a C header or Wasm component | `.vs` module with `extern` declarations (0.2, with the `extern` section) | bindings for a C library |
| `tool` | Adds a `verse <name>` subcommand or a debugger value renderer | what the user grants | what the user grants | `verse bench`, a renderer for a `Decimal` |

A package whose functions are compiled to a Wasm component is **not a plugin**:
it is an ordinary dependency (7.4). Only code that runs while your project
builds is a plugin.

Not extension points in 0.1: syntax, the type checker, the ownership checker,
the formatter (it has no options, §16.1), the optimizer, and the target
backends. Transforming passes are an open question (7.8).

## 7.3 Generators write source, and the source is visible

A generator's output is a normal `.vs` file in the `generated/` folder of the
package, starting with a header that says who made it and from what:

```verse
## Generated by `jsonschema` 1.2.0 from `schema/item.json`. Do not edit.
## Run `verse generate` to refresh it.

export type Item
    id: Int
    title: Text
```

- Generated files are checked by the compiler like any other file. No rule is
  relaxed for them: ownership, no shadowing, exports and `verse.api` all apply.
- They are committed or rebuilt by `verse generate`, never produced silently
  during `verse run`. A reader can open the file and read what runs.
- Generation is requested in `verse.toml` or on the command line, **never by
  an annotation in source**, because an annotation would be new syntax.
- Same inputs and same plugin version give the same bytes (spec §16.3).

## 7.4 Wasm-implemented packages are ordinary packages

A package may write its functions as a Wasm component instead of Verse source
(a GUI toolkit, a PLC driver). It is **not a plugin**, because it runs no code
while your project builds; it only becomes part of your program, like any other
dependency. So it is listed under `[dependencies]`, a published package can
depend on it, and no root-only rule applies. It is imported with the normal form:

```verse
import window, button from gui
```

It shows up in the build only if the program reaches it ([06](stdlib-and-shaking.md)).
Its exported signatures live in a `verse.api` file like any package, so the
compiler never needs its implementation to check a caller. The capabilities it
may reach are declared in its `[library] capabilities` (§16.3) and are visible
to `verse update` and to `[capabilities] grant` in the application.

**How a Wasm-implemented package runs inside a native binary (decision, Bob).** It is translated ahead of time, never run by an embedded engine, in every tier. A Wasm frontend lowers the component's functions to mono MIR, so the same optimizer, reachability analysis and backends handle it as handle Verse source. This keeps three promises: only reached functions are built in ([06](stdlib-and-shaking.md)), script mode and compile mode behave the same (tier 0 runs the translated MIR, so `verse run` needs no engine either), and no engine is added to the binary. On the Wasm target the component is linked directly. A package may import only its declared capabilities, and a component using Wasm features the frontend cannot lower is rejected at build time with a message naming the feature. See [ADR-0005](../decisions/0005-wasm-component-plugins.md) and [04 §4.4](backends-and-targets.md).

## 7.5 Trust and grants

- **Opt-in at the root project only.** Spec §16.3 says a dependency cannot
  run code at build time. Plugins keep that promise: only the root `verse.toml`
  may list plugins, and a dependency that needs one says so in its docs. A
  Wasm-implemented package is not a plugin (7.4) and may be a dependency of
  anything.
- **Sandboxed by default.** A plugin runs in a Wasm sandbox with no file
  system, no network, no clock, no randomness and no environment. It gets
  only the inputs and capabilities the root project grants.
- **Pinned.** `verse.lock` records each plugin's version and content hash.
- **Bounded.** Each run has a fuel, time and memory budget. A plugin that
  exceeds it is stopped, and the failure names the budget.

```toml
[plugins]
jsonschema = { version = "1.2", kind = "generator", reads = ["schema/"], writes = ["generated/"] }
style      = { version = "0.4", kind = "lint" }
```

A plugin's manifest states the capabilities it asks for. The tool shows the
request and the grant side by side, and refuses to run if the manifest asks
for more than `verse.toml` grants.

## 7.6 What plugins may say, and how

Plugin output uses the same diagnostic record as the compiler (§2.8), so
editors, `check --json` and the debugger treat it alike.

| Rule | Why |
|------|-----|
| A plugin code is `plugin-name/rule`, for example `style/prefer-map`. It never uses the `V` prefix | The reader can tell at a glance whether the language or a plugin is speaking |
| Severity is at most `warning`. The project may promote a rule to `error` in `verse.toml` | A plugin cannot block a build the project owner did not choose to block |
| A plugin cannot suppress, downgrade or reword a compiler diagnostic | Ownership and type errors must be the same everywhere |
| Messages follow §16.2: plain words, point at the exact code, suggest the fix | Plugin errors are part of the language's voice |
| Every suggestion is a machine-applicable edit or absent | An LLM or an editor can apply it without parsing prose |
| Every diagnostic names the plugin and its version | `verse explain style/prefer-map` knows where to look |

## 7.7 Discoverability

- `verse plugins` lists installed plugins with kind, version and grants.
- `verse why <path>` (the same command as `verse why <item>`, 19 §19.11) says whether a file was written by a generator, and which
  one.
- `verse check --json` marks each diagnostic with `source: "compiler"` or the
  plugin name.
- Documentation (`verse doc`) shows generated items with a "generated by" note.

## 7.8 Open questions

1. **Transforming passes.** A pass that rewrites mono MIR could break the
   guarantee that all tiers behave alike. Proposal: not in 0.1. If added later,
   it must be verified by the differential tests ([10](testing-and-verification.md))
   and declared `pure`.
2. **User-defined derives.** `Show`, `Eq` and friends are derived structurally.
   Proposal: user-defined derivation is a `generator` that writes `impl` blocks
   for the types listed in `verse.toml`. It needs no syntax, but it needs a
   ruling that generated `impl`s in the same module are allowed (§10.1).
3. **`extern` declarations**. `bindgen` cannot ship before the
   language has a stable form for them.
4. **Plugin discovery by name.** Registry trust, signing and revocation belong
   to the package manager design and are not decided here.
5. **Wasm-implemented packages inside native binaries.** Ruled by Bob in §7.4: ahead-of-time translation to mono MIR in every tier, with no embedded engine, not even for `verse run`. This replaces the earlier proposal that kept an engine for `verse run`, because an engine would make script and compile modes differ.
